    Assumptions and limits

    What the whole model takes for granted. Worth reading before betting a download on it.

    Speed is bandwidth, not compute

    Generation is treated as purely memory-bandwidth bound, because reading every active weight dominates. That holds for single-stream local inference on the hardware here. It breaks down for batched serving, for very small models on fast memory, and anywhere compute is the real ceiling.

    One number for a whole memory pool

    Each device gets a single effective bandwidth. Real machines vary by access pattern, thermal state, and what else is resident. Treat every tok/s as a ceiling you approach, not a promise.

    KV estimates fail by architecture

    Extrapolating KV from parameter count assumes full attention on every layer. Sliding-window models cap the cache instead: gemma4:12b-it-qat was estimated at 48 MB per 1k tokens and measured at 3.1. Anything not tagged measured can be wrong by an order of magnitude.

    Placement is predicted, not observed

    The CPU/GPU split is inferred from budgets. The runtime decides for real, and may keep more or fewer layers resident than modelled, especially near the boundary.

    Overhead is a flat allowance

    A fixed 0.6 GB stands in for compute buffers and runtime working memory. It actually varies with batch size, context, and backend, and is the least defensible constant in the model.

    Fit is not capability

    Everything here is about bytes and bandwidth. A model that fits comfortably may still be worse at your task than one that barely runs. Quantisation especially trades quality for size in ways no number on this page captures.

    How the numbers are derived. Generation is memory-bandwidth bound: every token requires reading every active weight, so tok/s ≈ effective bandwidth ÷ active weight bytes. Ultron's 83 GB/s constant is measured — qwen3.5:9b, 5.4 GB of weights, 15.4 tok/s observed. Other bandwidths are vendor figures derated to ~80%, flagged est.

    Why spilling hurts your two machine types differently. Effective bandwidth is blended harmonically across the fast and slow pools. On unified memory the slow pool is the same physical RAM, so a 45% CPU split costs about 10% — measured. On a discrete GPU the slow pool is across PCIe, so the same split is catastrophic. One word, two behaviours.

    MoE models. Memory tracks total parameters; speed tracks active parameters. A 30B/3.3B-active model occupies like a 30B and generates like a small dense model.

    Where the model specs come from. Parameter counts, trained context, and per-quant file sizes are read from the Hugging Face API for each GGUF repo, with split shards summed and vision projectors excluded.

    KV estimates are the weakest number here, and they fail by architecture. Where a model is not marked measured, its KV cost is extrapolated from parameter count — which assumes every layer keeps a full cache. Models tagged SWA use sliding-window attention and cap the cache instead of growing it: gemma4:12b-it-qat was estimated at 48 MB per 1k tokens and measured at 3.1, a 15-fold error, with resident size essentially flat from 4k to 131k context. Measure before trusting an estimate on a long-context plan.
